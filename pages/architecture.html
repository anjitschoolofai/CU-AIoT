L1
Physical / Sensing Layer Sensing
DHT22 · DS18B20 · PIR · HC-SR04 · Soil Moisture · LDR · MQ-135 · MPU6050
Responsible for physical measurement, analog-to-digital conversion, and basic actuation. This is where the physical world meets the digital — every byte in your AIoT system originates here.

Key responsibilities: Measure physical phenomena · Convert to electrical signals · ADC sampling · Initial conditioning

L2
Connectivity & Messaging Layer Transport
Wi-Fi 802.11 · BLE 5.0 · Zigbee · LoRaWAN · MQTT v5 · HTTP/HTTPS · CoAP · WebSockets
Handles reliable data transport from sensors to processing systems. Includes message queuing, protocol translation, and QoS guarantees. Protocol selection at this layer fundamentally shapes system latency, power consumption, and cost.

Key responsibilities: Reliable delivery · Message queuing · Protocol bridging · QoS negotiation · Encryption (TLS)

L3
Edge & Embedded Processing Layer Edge
ESP32 · Raspberry Pi 4 · NVIDIA Jetson Nano · Arduino (limited) · STM32 · BeagleBone
Performs local inference, data filtering, aggregation, and protocol bridging. Edge processing reduces latency to milliseconds, preserves privacy by keeping data local, and reduces cloud bandwidth/cost by pre-processing before upload.

Key responsibilities: Real-time filtering · Moving average smoothing · Local rule evaluation · Protocol translation · Firmware OTA updates
›
↓
L4
Cloud & Data Platform Layer Cloud
AWS IoT Core · Azure IoT Hub · ThingsBoard · InfluxDB · Node-RED · TimescaleDB · Apache Kafka
Provides long-term storage, global accessibility, and scalable stream processing. Cloud platforms enable data from thousands of devices to be aggregated, visualized, and analysed. Trade-off: requires internet connectivity and introduces latency.

Key responsibilities: Time-series storage · Multi-device aggregation · Historical analysis · Rule engine · REST/WebSocket APIs
›
↓
L5
AI / ML Analytics Layer Analytics
Python · scikit-learn · TensorFlow Lite · ONNX Runtime · Isolation Forest · Linear Regression · Decision Trees
Applies machine learning and statistical models to sensor data for pattern recognition, prediction, and anomaly detection. For most campus applications, simple models (threshold rules, linear regression) outperform complex models and are far easier to explain and maintain.

Key responsibilities: Anomaly detection · Trend prediction · Classification · Recommendation generation · Model serving
›
↓
L6
Application, Visualization & Decision Layer Application
Grafana · ThingsBoard Dashboards · Custom React/Vue Apps · Mobile Apps · Actuator APIs · Webhooks
The human-facing output layer — where decisions are displayed, alerts sent, and actuators triggered. Design here should prioritize clarity: operators must be able to understand alerts and take action within seconds. Closed-loop control (auto-actuation) requires safety interlocks.

Key responsibilities: Real-time visualization · Alert management · Actuator control · Report generation · Human-in-the-loop confirmation

Data Flow Trace Step-by-step: temperature sensor → dashboard alert

Follow a single temperature reading as it travels through all 6 layers of the AIoT stack.

Steps highlight automatically every 1.5 seconds
1
Layer 1 — Physical Sensing
Temperature sensor reads 31.2°C
DHT22 sensor samples every 2 seconds. Internal ADC converts thermistor resistance to digital value. Output: 12-bit integer = 3120 (represents 31.20°C × 100)
↓
2
Layer 1→2 — Signal & GPIO
DHT22 outputs 1-wire digital signal → ESP32 reads via GPIO pin
GPIO pin 4 set as INPUT_PULLUP. ESP32 reads 1-wire protocol timing. Raw value: 31.2°C. No noise filtering yet — raw reading passed to processing.
↓
3
Layer 3 — Edge Processing (ESP32)
ESP32 applies moving average filter to remove noise
5-point moving average: [30.8, 31.0, 31.1, 31.3, 31.2] → avg = 31.08°C. Spike filter: if |new - prev| > 5°C then discard. Filtered value: 31.1°C
↓
4
Layer 2 — MQTT Publish
ESP32 publishes JSON payload to MQTT topic
Topic: campus/room101/temperature
Payload: {"value": 31.1, "unit": "C", "device": "CAMPUS-TEMP-01", "ts": 1762128000}
QoS Level 1 (at least once delivery). TLS 1.3 encrypted.
↓
5
Layer 4 — Cloud Platform (ThingsBoard)
ThingsBoard MQTT broker receives and stores reading
Message received at MQTT broker port 8883. ThingsBoard parses JSON and writes to InfluxDB time-series: measurement="temperature", device="room101", value=31.1. Dashboard auto-updates via WebSocket.
↓
6
Layer 5 — AI/ML Analytics (Isolation Forest)
Isolation Forest anomaly detector scores reading as 0.82 (elevated)
Model trained on 30-day historical data (baseline: 24–28°C). Isolation score 0.82 → above threshold 0.75. Classification: ANOMALY. Confidence: 82%. Method: Isolation Forest (unsupervised, no labelled data needed)
↓
7
Layer 6 — Application & Decision
Dashboard alert: "Temperature elevated — recommend ventilation"
ThingsBoard rule chain triggers: 1) Push notification to facility manager app. 2) Email alert to room coordinator. 3) Actuator command sent to HVAC REST API: POST /api/hvac/room101 {"mode": "cool", "temp": 24}. 4) Alert logged to audit trail.

MQTT is the de-facto standard for IoT messaging. A lightweight pub/sub protocol designed for constrained networks and devices. The broker decouples publishers from subscribers — devices publish data to topics, and any number of subscribers receive it without needing to know each other.

Publisher (ESP32 — MicroPython)
from umqtt.simple import MQTTClient
import ujson, time

CLIENT_ID = b"campus-esp32-01"
BROKER    = b"192.168.1.100"   # Local MQTT broker IP
TOPIC     = b"campus/room101/temperature"

client = MQTTClient(CLIENT_ID, BROKER, port=1883)
client.connect()

while True:
    temp = read_dht22_temperature()    # your sensor function
    payload = ujson.dumps({
        "value": temp,
        "unit": "C",
        "device": "CAMPUS-TEMP-01",
        "ts": time.time()
    })
    client.publish(TOPIC, payload, qos=1)
    time.sleep(2)
Subscriber (Python — paho-mqtt)
import paho.mqtt.client as mqtt, json

def on_message(client, userdata, msg):
    data = json.loads(msg.payload)
    print(f"[{msg.topic}] Temp: {data['value']}°C")
    if data['value'] > 30:
        trigger_alert(data)          # your alert function

client = mqtt.Client()
client.on_message = on_message
client.connect("192.168.1.100", 1883)
client.subscribe("campus/+/temperature", qos=1)  # wildcard: all rooms
client.loop_forever()

HTTP/REST is familiar, widely supported, and excellent for configuration APIs, bulk data upload, and integration with web services. Not ideal for high-frequency telemetry (polling is inefficient) but great for actuator commands and dashboard data retrieval.

POST Sensor Data (ESP32 Arduino)
#include <WiFi.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>

const char* SERVER = "https://api.thingsboard.io/api/v1/TOKEN/telemetry";

void postSensorData(float temp, float humidity) {
    HTTPClient http;
    http.begin(SERVER);
    http.addHeader("Content-Type", "application/json");

    StaticJsonDocument<128> doc;
    doc["temperature"] = temp;
    doc["humidity"]    = humidity;
    String payload;
    serializeJson(doc, payload);

    int code = http.POST(payload);
    Serial.printf("HTTP %d: %s\n", code, payload.c_str());
    http.end();
}
⚠️
When to prefer MQTT over HTTP: If your sensor sends data more than once every 5 seconds, HTTP overhead becomes significant. For high-frequency telemetry (>1 Hz), use MQTT. Use HTTP for: configuration changes, bulk historical upload, actuator commands, webhook integrations.

CoAP is designed for constrained nodes and networks — it is essentially HTTP semantics (GET, POST, PUT, DELETE) over UDP, with a 4-byte binary header instead of HTTP's 200+ byte text headers. Ideal for battery-powered sensors on low-power networks (6LoWPAN, Zigbee, NB-IoT).

CoAP Client (Python — aiocoap)
import asyncio, aiocoap

async def post_sensor():
    protocol = await aiocoap.Context.create_client_context()

    payload = b'{"temp": 31.2, "unit": "C"}'
    request = aiocoap.Message(
        code   = aiocoap.POST,
        uri    = 'coap://192.168.1.50/sensors/temperature',
        payload= payload
    )
    response = await protocol.request(request).response
    print(f"CoAP response: {response.code}")

asyncio.run(post_sensor())

Role in AIoT
Dashboard live updates · Browser-to-cloud

WebSockets provide a persistent, full-duplex channel between browser and server — essential for live dashboards that update in real time. In AIoT systems, WebSockets typically appear at the Application layer (L6): the cloud platform pushes sensor updates to the dashboard browser via WebSocket, eliminating the need for inefficient polling.

Browser Dashboard (JavaScript)
// Connect to ThingsBoard WebSocket subscription
const token  = 'YOUR_DEVICE_TOKEN';
const wsUrl  = `wss://thingsboard.io/api/ws/plugins/telemetry?token=${token}`;
const socket = new WebSocket(wsUrl);

socket.onopen = () => {
  // Subscribe to telemetry keys
  const cmd = { tsSubCmds: [{ entityType: "DEVICE", entityId: "...",
                  scope: "LATEST_TELEMETRY", cmdId: 1 }], attrSubCmds: [] };
  socket.send(JSON.stringify(cmd));
  console.log("WebSocket connected — live updates active");
};

socket.onmessage = (event) => {
  const data = JSON.parse(event.data);
  const temp = data.data?.temperature?.[0]?.[1];
  if (temp !== undefined) {
    document.getElementById('temp-display').textContent = temp + '°C';
    updateChart(temp);      // your Chart.js update function
  }
};
💡
WebSocket vs MQTT over WebSocket: MQTT itself can run over WebSocket (MQTT/WS on port 9001) — this is how browser-based MQTT clients work (e.g., MQTTX Web). ThingsBoard and other platforms expose WebSocket APIs for dashboard subscriptions, combining MQTT's pub/sub model with browser compatibility.

Edge vs Cloud Decision Matrix When to process where

Use this matrix when designing your AIoT system's processing architecture. Many production systems use hybrid approaches — edge for latency-critical decisions, cloud for long-term analytics.

Criterion / Requirement → Edge → Cloud → Both (Hybrid)
Latency < 10 ms required
e.g., motor stop, safety shutoff		 ✅ Edge only
Cloud adds 50–500ms		 ✗ ✗
Privacy-sensitive data
e.g., medical, biometric, CCTV		 ✅ Process + store locally ✗ Legal/GDPR risk ⚡ Anonymise at edge, send aggregates to cloud
Unreliable internet connectivity
e.g., rural campus, construction sites		 ✅ Must work offline ✗ Single point of failure ⚡ Edge-first with cloud sync when online
Large-scale ML model training
e.g., multi-week anomaly model		 ✗ Insufficient compute ✅ Cloud GPU/TPU instances ✗
Real-time alerts (< 1 second)
e.g., fire, gas leak, vibration alarm		 ✅ Local threshold rules ✗ Too slow for safety ⚡ Alert at edge + log to cloud
Long-term data storage (months+)
e.g., regulatory compliance, trend analysis		 ✗ Local storage limited ✅ Scalable cloud storage ⚡ Cache at edge, archive to cloud
High compute ML inference
e.g., image classification, NLP		 ✗ Except Jetson/RPi with TFLite ✅ Full model in cloud ⚡ Lightweight model at edge, full model in cloud
Multi-site aggregation
e.g., campus + 5 remote buildings		 ✗ No cross-site visibility ✅ Central aggregation ⚡ Each site has edge; cloud aggregates all
Cost-sensitive deployment
e.g., university budget constraints		 ✅ One-time hardware cost ✗ Ongoing subscription fees ⚡ Edge for data, free-tier cloud for dashboards
Firmware & OTA updates needed
Managing 50+ sensor nodes		 ✗ Hard to scale locally ✅ Cloud OTA management platforms ⚡ Cloud-triggered, edge-executed
✅
Recommended for campus AIoT (starting point): Hybrid architecture — ESP32/RPi edge devices run local threshold rules and alert immediately; summary data is sent to a free ThingsBoard Community Edition instance for dashboards and historical storage. Upgrade to cloud-managed services as scale grows.
