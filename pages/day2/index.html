Module 2 — Smart-System Design Methodology A 14-step repeatable workflow

Apply this workflow to any AIoT design problem — from a simple classroom monitor to a complex industrial predictive maintenance system.

1
Problem Identification

Define the pain point. Quantify impact. Confirm that AIoT adds value over simpler solutions.

❓ What specifically is the problem? Who is affected? What is the cost of inaction?
2
Requirements Analysis

Gather functional and non-functional requirements. Identify stakeholders, constraints and success criteria.

❓ What must the system do? How fast/reliable/private/cheap must it be?
3
Sensing Strategy

Identify what physical quantities to measure, appropriate sensor types, placement, sampling rates and calibration needs.

❓ What physical phenomenon indicates the problem? Which sensor measures it reliably?
4
Device & Hardware Selection

Choose microcontroller/SBC based on compute, power, connectivity, cost and AI requirements.

❓ Does inference need to run locally? What is the power budget? Is battery needed?
5
Connectivity Planning

Select wireless/wired protocol based on range, data rate, power, topology and infrastructure availability.

❓ How far is the gateway? How often does data need to arrive? Is internet available?
6
Edge/Cloud Partitioning

Decide which processing happens at the edge vs cloud based on latency, privacy, bandwidth and compute needs.

❓ What decisions need to be made instantly? What data must not leave the device?
7
Data Pipeline Design

Define data schema, ingestion path, storage format, time-series structure and data quality checks.

❓ What is the JSON/CSV schema? Where is it stored? How are missing values handled?
8
AI/ML Method Selection

Choose the appropriate algorithm based on labelled data availability, problem type, and required explainability.

❓ Is this classification, regression, or anomaly detection? Do we have labeled fault data?
9
Decision & Action Design

Define what the system does with predictions — alerts, actuator commands, reports. Include safety conditions.

❓ What happens when the model detects an anomaly? Who is notified? What is the fail-safe?
10
User Interface Design

Design dashboards, mobile alerts, and access control for different user roles (operator, manager, admin).

❓ Who views the dashboard? What do they need to see immediately vs on demand?
11
Security Planning

Define authentication, encryption, network segmentation, data access controls and update mechanisms.

❓ Who can access device data? How are credentials managed? How is firmware updated securely?
12
Testing Strategy

Plan unit tests (sensor reading), integration tests (end-to-end pipeline), and validation tests (model performance).

❓ What constitutes a passing test? How is model accuracy validated on new data?
13
Deployment Planning

Plan device provisioning, physical installation, initial configuration and rollout sequence.

❓ How are 50 devices configured consistently? What is the rollback plan if deployment fails?
14
Monitoring & Maintenance

Define ongoing observability: model drift detection, sensor health checks, firmware update schedule and data retention.

❓ How do we know the model is still accurate 6 months later? What triggers recalibration?

Module 3 — Application Architecture Patterns

Each pattern is a proven solution template for a class of AIoT design problems. Understanding patterns helps you select and combine the right approach for a new use case.

📊
Monitoring & Alerting

Continuous sensor reading + threshold alerts. Simplest and most common pattern. When to use: Environmental monitoring, equipment health checks. Limitation: High false-alarm rate if thresholds are fixed.

🔄
Closed-Loop Control

Sensor reading → decision → actuator command in a continuous loop. When to use: HVAC, irrigation pumps, industrial process control. Limitation: Requires safety fail-safes; dangerous if actuator misbehaves.

🔮
Predictive Systems

ML model predicts future states (failure, demand, yield). When to use: Predictive maintenance, energy forecasting, crop yield. Limitation: Requires sufficient labelled historical data; accuracy degrades with data drift.

🌐
Distributed Sensing

Many sensor nodes feeding a centralised aggregator. When to use: Wide-area monitoring (smart city, precision agriculture). Limitation: Network reliability, time synchronisation, data fusion complexity.

⚖️
Edge-Cloud Collaboration

Edge handles latency-sensitive inference; cloud handles ML training, storage, dashboards. When to use: Most production AIoT systems. Limitation: Adds architectural complexity; synchronisation needed.

🪞
Digital Twins

A virtual replica of a physical system updated in real-time by sensor data. When to use: Industrial assets, buildings, supply chains. Limitation: Significant engineering effort to build and maintain the model fidelity.

🧑‍💼
Human-in-the-Loop

AI recommends; human approves before action. Critical for safety-sensitive decisions. When to use: Medical alerts, critical infrastructure, financial decisions. Limitation: Slower response; human may be unavailable.

🤝
Federated Learning

Model is trained across many devices without sharing raw data. When to use: Privacy-sensitive distributed sensing (healthcare, personal devices). Limitation: Active research area; complex to implement reliably in production. ⚠️ EMERGING RESEARCH

Module 4 — Sector-Based Design Studios

⚠️All healthcare examples are EDUCATIONAL ONLY. Not validated clinical systems. Not medical advice or certified medical devices.
Problem Statement

Remote patient monitoring in ICU wards requires continuous vital sign tracking. Gaps in observation can lead to delayed detection of deterioration. Nurse-to-patient ratios are constrained.

Sensors & Devices

Pulse oximeter (SpO₂), ECG electrodes, blood pressure cuff, skin temperature, accelerometer (fall detection), smart bed pressure sensor

AI Method

Threshold rules for immediate vital sign alerts (RULE-BASED — not ML). Statistical anomaly detection for deterioration pattern. Note: Any use in clinical settings requires regulatory approval (FDA/CE/CDSCO).

Architecture Flow
🩺 Wearable sensors → BLE → Bedside ESP32 hub
⚙️ Edge: Vital sign validation, immediate threshold alerts
📡 Wi-Fi/Ethernet → Hospital server
☁️ Nurse station dashboard + alarm system
🤖 Statistical: rolling window anomaly scoring
🧑‍⚕️ Human-in-the-loop: nurse confirms before any intervention
Limitations & Risks

False alarms (alarm fatigue), sensor artefacts from patient movement, regulatory compliance requirement, data privacy (patient data is sensitive), network reliability in hospital environment

Problem Statement

Farmers over-irrigate due to lack of real-time soil data, wasting water and affecting crop yield. Manual monitoring of 50+ plots is impractical.

Sensors

Soil moisture (capacitive), soil temperature, ambient temperature and humidity, rainfall gauge, solar radiation sensor

AI Method

RULE-BASED: If soil moisture < threshold for crop type → recommend irrigation. A TRAINED ML MODEL (Decision Tree or Random Forest) trained on historical data + weather can predict optimal irrigation time. Clearly label which is in use.

Architecture
🌱 Soil sensors → LoRaWAN (long range, low power)
🔌 LoRa gateway (Raspberry Pi) at farm office
⚙️ Edge: Threshold check, pump relay control
☁️ Cloud: Historical data, ML model training, weather API integration
📱 Farmer mobile app: alerts and manual override
Expected Benefit / Limitations

Potential water saving (illustrative; actual saving depends on baseline and crop type). Limitations: LoRaWAN coverage, sensor drift in wet soil, crop-specific threshold variation, weather forecast accuracy.

Problem Statement

Unplanned equipment failure in manufacturing causes costly downtime. Maintenance teams lack early warning of impending failures.

Sensors

Triaxial accelerometers (vibration), current transformers (motor load), infrared thermometers (bearing temperature), acoustic emission sensors

AI Method

Isolation Forest for anomaly detection (UNSUPERVISED — learns normal vibration pattern, flags deviations). Important: Requires collecting baseline data during normal operation. Cannot detect fault types without labelled fault data. Do not claim predictions are validated until the model is tested on real failure events.

Deployment Checklist
  • ✓ Collect 2–4 weeks of baseline vibration data (normal operation)
  • ✓ Validate sensor mounting and sampling rate (≥1kHz for bearing faults)
  • ✓ Train Isolation Forest on baseline data
  • ✓ Set anomaly score threshold with maintenance team input
  • ✓ Run parallel with existing schedule for 1 month before trusting predictions
  • ✓ Integrate with CMMS (Computerised Maintenance Management System)
  • ✓ Plan model retraining schedule (quarterly or after maintenance)
Problem Statement

University buildings consume energy in unoccupied spaces. Lack of granular monitoring makes it impossible to identify waste or set realistic reduction targets.

Sensors

Smart energy meters (per room/floor), PIR occupancy sensors, HVAC run-time sensors, solar production meter

AI Method

RULE-BASED: If room unoccupied for >15 min AND HVAC running → alert. STATISTICAL: Moving average baseline comparison for anomaly detection. TRAINED ML: LSTM or linear model for next-day demand forecast (label as ILLUSTRATIVE until validated on actual data).

Architecture
⚡ Smart meters → Modbus/RS485 → Building gateway
👁️ PIR sensors → Zigbee mesh → Same gateway
⚙️ Edge: Occupancy-linked HVAC scheduling
☁️ InfluxDB + Grafana dashboard
📊 Monthly energy reports with baseline comparison
Problem Statement

Urban traffic congestion, inefficient street lighting, and unmonitored air quality reduce quality of life and increase municipal costs.

Sensors

Inductive loop detectors / radar (vehicle count), PM2.5/PM10 air quality sensors, sound level meters, smart waste bin fill sensors, water quality probes

Connectivity

LoRaWAN for distributed low-power sensors; 4G/5G cellular for high-bandwidth nodes (cameras); fibre for fixed infrastructure

AI Methods
  • Traffic: Adaptive signal timing using vehicle count + time-of-day rules (RULE-BASED)
  • Street lighting: Daylight sensor + PIR — threshold-based dimming (RULE-BASED)
  • Waste: Fill-level threshold alert → optimised collection routing (RULE-BASED + optimisation algorithm)
  • Air quality: Statistical threshold alerts for PM2.5 exceedances (WHO guidelines)
ℹ️Smart city systems involve significant regulatory, privacy and governance considerations. Citizen data collection requires transparent policy and consent frameworks.

Module 5 — AIoT Data & Model Engineering

Data Pipeline Steps
  1. Define data schema (fields, types, units, timestamp format)
  2. Collect representative data across expected operating conditions
  3. Label data (for supervised learning — fault vs normal)
  4. Handle missing values (interpolation, flagging, rejection)
  5. Handle data drift — statistical shift in feature distributions over time
  6. Feature engineering — extract meaningful statistics (mean, RMS, FFT peaks)
  7. Train-validation-test split
  8. Select and train model; evaluate on test set
  9. Deploy model (edge: TFLite; cloud: scikit-learn API)
  10. Monitor model performance in production; schedule retraining
Model Selection Guide
ScenarioRecommended Approach
No labelled fault dataIsolation Forest / statistical anomaly
Many labelled classesRandom Forest / SVM
Time-series predictionLinear Regression / LSTM
Pattern groupingK-Means clustering
Constrained edge deviceDecision Tree / TinyML (quantized)
Simple threshold sufficientRule-based (don't over-engineer)
💡A well-calibrated threshold rule that works reliably is often better than a complex ML model that is hard to validate. Choose the simplest approach that meets requirements.

Module 6 — Integration, Reliability & Deployment

Deployment-Readiness Checklist
0/10 items checked
Fault Tolerance Strategies
  • Store-and-forward: cache data locally if network drops
  • Watchdog timers: auto-restart device if firmware hangs
  • Redundant sensors for critical measurements
  • Heartbeat monitoring: detect silent device failure
  • Graceful degradation: system continues with reduced capability
  • OTA (Over-the-Air) firmware updates for field devices

Module 7 — Security, Ethics & Sustainability by Design

🔒 Security
  • TLS everywhere — MQTT, HTTP
  • Device identity certificates
  • Principle of least privilege
  • Secure firmware updates (signed)
  • Penetration testing before deployment
🧑‍⚖️ Ethics & Privacy
  • Informed consent for data collection
  • Data minimisation principle
  • Explainable AI decisions
  • Bias audit of training data
  • Human oversight for high-stakes decisions
♻️ Sustainability
  • Low-power hardware selection
  • Sleep modes and duty cycling
  • Local processing reduces data transmission
  • Component lifecycle and e-waste plan
  • Renewable power (solar harvesting) where feasible
